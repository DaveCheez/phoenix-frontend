## Status words

- Implemented: the behaviour is in a named commit.
- Tested: a recorded local or isolated check exists. The transcript stays in the linked document.
- Merged: the commit is in the named production source branch.
- Deployed: a recorded live revision proves it. A checked-in app spec is not that proof.
- Deferred: agreed, and not part of the current release.

Committed does not mean merged. Merged to a feature branch does not mean deployed.

## Standing commercial terms

These remain in force. They are not permission to enable checkout.

- Workshop fitting only, at the Accrington workshop. Delivery is not offered.
- Fitting is included at no charge.
- Prices do not add a VAT charge.
- A future checkout takes a one-third deposit. The balance is due on completion.
- Deposit and balance are calculated on the server from the agreed order total.
  `orders/money.py` on the foundation branch uses
  `deposit_pence = (total_pence + 1) // 3`.
- The cart page already states workshop fitting and no delivery. Lead time,
  the no-charge fitting statement, and the no-VAT statement are not yet a
  complete customer-facing price explanation. PV-COPY remains open.

## 3. Release blockers, in dependency order

1. PV-AUTODEPLOY. Read the live DigitalOcean settings for both apps. The checked-in specs set `deploy_on_push: true` (frontend branch `master`, backend branch `main`). Whether the live apps match those specs is UNVERIFIED. Turn autodeploy off, on the platform and in any workflow, before merging to those branches. The backend spec names `DaveCheez/pheonix`; the configured remote is `DaveCheez/phoenix`. Resolve that before trusting the spec.
2. PV-CONTACT. Enquiry delivery is still a current priority. It is not in either candidate. Frontend `feature/contact-enquiries` `63df13a` (29 September 2026) is one commit diverged from `f6ae1ab`, which is behind `master`. Backend `feature/contact-enquiries` `96e9eaf` is one commit diverged from `27b469d`, which is behind `main`. Neither fast-forwards. Real delivery to the Phoenix Vanz inbox, including Reply-To, is not recorded. A HTTP 200 is not acceptance. Do not drop this work and do not merge it silently.
3. PV-MIGRATE. Plan and rehearse backup and restore before applying the foundation migrations that are not on `main`: `cart` `0004` through `0006`, and `orders` `0001` through `0005`. Django 5.2 adds none. Contact adds `store/migrations/0026_enquiry.py`, which uses the same number as `store/migrations/0026_product_option_configuration.py` already on `main`. Do not renumber a migration production has applied. Whether production has applied `0026_product_option_configuration` is UNVERIFIED. The enquiry migration has to be sequenced after the applied chain, not rewritten over it.
4. PV-MAINT-MODE. A tested way to stop basket writes, including direct Django API paths, during the cutover. The counter cleanup command is not that mechanism. None was found in the candidate source. Do not claim a staging app or a monitor exists.
5. PV-STAGE. Deploy this exact pair to a production-like staging environment. No such environment is recorded. Preserve homepage, product-option and Elfsight behaviour that may already be live. Staging is not the isolated local PostgreSQL containers used for verification.
6. PV-QUOTA. Approve production budget values and the maintenance cadence, batch caps, deadline and alert recipients before enforcement or a scheduled job is turned on. Test-only policies in the verification docs are not those values.
7. PV-SMOKE. After backend migration and deploy, deploy the matching frontend. Then HTTPS smoke of homepage, contact, basket start, add, recovery and health, before the basket is reopened. Record the deployed revision of each app.
8. PV-ROLLBACK. Compatible paired rollback or an explicit fix-forward. Rolling the app back must not restore UUID-only basket ownership. Rolling the app back does not undo database migrations.

## 4. Deferred work

### PV-CHECKOUT — Stripe deposit and balance payment

Deferred. Do not enable `NUXT_PUBLIC_CHECKOUT_ENABLED` or production payment keys as part of the guest-cart release.

Preserved requirements, still unmet:

- one-third deposit at checkout, balance due on completion, both calculated on the server;
- durable order before payment, with deposit, outstanding balance and payment status;
- webhook signatures, idempotency and duplicate-payment protection;
- order-confirmation and balance-payment pages from a real order reference;
- payment email only after a verified webhook;
- workshop fitting, lead time and balance terms visible before payment;
- Django-admin visibility and a manual fallback while a provider is down.

Historical failure to preserve: an invalid Stripe API key previously broke the unfinished checkout. Correcting that key is part of this deferred implementation. It is not permission to turn payments on. The browser key, when this work starts, must be a publishable `pk_test_` or `pk_live_` key. A secret key does not belong in the frontend.

### PV-REVIEWS — first-party Google reviews

Deferred. Do not start it unless explicitly requested. Elfsight stays until a replacement is populated and approved. Then remove Elfsight, its third-party scripts and the obsolete review proxy together.

### PV-NUXT — further Nuxt upgrade

Pending. `master` and `feature/guest-cart-access` both pin Nuxt `3.21.11`, Node `>=22 <23`. The guest-cart release note says those supported versions are unchanged. A separate `phoenix-vanz-nuxt-django52` directory was not established as a worktree of this repository.

### PV-COPY and older open requirements

Still open. Not silently dropped:

- unique titles, canonical URLs, descriptions and social images on every indexable route, where PV-SEO did not already cover them;
- contact fields accessible and validated in line with the server, privacy wording, and product or source prefill;
- carousel hit area, logo accessible name, Elfsight iframe title, focus, keyboard and reduced motion;
- useful outage, empty and retry states without duplicate proxy storms;
- local seed command and `.env.example` files that name variables only;
- Nuxt `#app-manifest` development cache error and the `postcss.config.js` warning;
- frontend tests beyond the current cart-access script. Vitest and Playwright are not installed. Do not treat Edge CDP notes as a Playwright suite;
- CI remains a merge gate for the branches it already watches. Deployment must not proceed on a red check;
- post-deploy smoke for homepage, contact, cart, checkout, health and key APIs;
- product WebP optimiser and backfill, responsive image sizes, Spaces cache lifetime, older HomeSlide MIME types, SSR time-to-first-byte, and the navigation logo size;
- enquiry journey carrying the selected product and vehicle details;
- four-week lead time and vehicle-specific hinge requirements;
- order-status route with the order reference;
- email retry that cannot duplicate an enquiry or an order.

## Working rules

1. Tag or record the current known-good commit before risky work.
2. Use one feature branch per change.
3. Generate changes against the exact current commit.
4. Apply small, reviewable patches.
5. Never replace existing workflows wholesale.
6. Run available local checks and GitHub CI.
7. Merge through a pull request.
8. Deploy only after CI passes.
9. Update this file when a task changes status. Committed is not merged, and merged is not deployed.
