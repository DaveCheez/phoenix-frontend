## Status words

- Implemented: the behaviour is in a named commit.
- Tested: a recorded local or isolated check exists. The transcript stays in the linked document.
- Merged: the commit is in the named production source branch.
- Deployed: a recorded live revision or owner-confirmed live behaviour proves it. A checked-in app spec is not that proof.
- Deferred: agreed, and not part of the current work.

Committed does not mean merged. Merged does not, by itself, mean deployed.
One live basket check does not mark the rest of the release production-tested.

## Next

Public confirmation comes before taking money. PV-ORDERS stays the internal
model. It is not this API. PV-ORDER is the next development milestone.

1. PV-ORDER — order reference and confirmation. A shopper can be given a real order
   reference and open that order's status. No Stripe and no deposit capture
   in this step.
   Done when: a durable order created by Phoenix Vanz can be opened from its
   reference without a payment.

2. PV-CHECKOUT — one-third deposit, then the balance on completion.
   Still unmet. Do not enable `NUXT_PUBLIC_CHECKOUT_ENABLED` as part of the
   items in Now.
   - Deposit and balance are calculated on the server from the order total.
   - The order exists before payment, with deposit, outstanding balance, and
     payment status.
   - Webhook signatures, idempotency, and duplicate-payment protection.
   - Confirmation and balance pages use a real order reference.
   - Payment email is sent only after a verified webhook.
   - Workshop fitting, lead time, and balance terms are visible before payment.
   - Django admin can see the order, and there is a manual fallback while a
     provider is down.
   The browser key, when this starts, must be a publishable `pk_test_` or
   `pk_live_` key. An invalid Stripe key previously broke the unfinished
   checkout. Correcting that key is part of this work. It is not permission
   to take payments.

## Working rules

1. Tag or record the current known-good commit before risky work.
2. Use one feature branch per change.
3. Generate changes against the exact current commit.
4. Apply small, reviewable patches.
5. Never replace existing workflows wholesale.
6. Run available local checks and GitHub CI.
7. Merge through a pull request.
8. Deploy only after CI passes.
9. Update this file when a task changes status. Committed is not merged, and merged is not deployed.
