## P0 — Revenue, Enquiries and Checkout

### Contact form and enquiry delivery
- [ ] **Contact form: deliver every genuine enquiry to Phoenix Vanz by email.**
  - Submit to a first-party Nuxt/Django endpoint; do not rely on `mailto:`.
  - Save the enquiry in Django before attempting email delivery so enquiries are not lost when the mail provider is unavailable.
  - Send from a verified Phoenix Vanz/domain address and set `Reply-To` to the customer's email address.
  - Configure the recipient through an environment variable such as `CONTACT_TO_EMAIL`; do not hard-code the personal address in the frontend.
  - Email subject should clearly identify a website enquiry and the customer's name/product where available.
  - Include: customer name, email, telephone, van make/model/year/length, product of interest, message, source page URL, submission time and enquiry reference.
  - Add server-side validation, honeypot/rate limiting, sanitisation and useful error logging.
  - Show clear sending, success and failure states in the frontend; preserve entered values after a failure.
  - Send a customer acknowledgement only after the Phoenix Vanz delivery succeeds.
  - Test real delivery to the configured Phoenix Vanz inbox in production, including `Reply-To`; a HTTP 200 response alone is not acceptance.

### Deposit checkout and payment
- [ ] **Stripe: finish and production-test the 1/3 deposit checkout.**
  - Customer pays one third at checkout; remaining balance is due on completion.
  - Calculate prices and the deposit on the server, not in the browser.
  - Correct Stripe environment variables and remove the previous invalid-key failure.
  - Create a durable order before payment and store deposit amount, outstanding balance and payment status.
  - Verify webhooks, signatures, idempotency and duplicate-payment protection.
  - Confirm the order-confirmation and balance-payment pages work from a real order reference.
  - Send Phoenix Vanz and the customer a payment/order email after a verified webhook event.
  - Make the workshop fitting, lead-time and balance terms clear before payment.

### Order and enquiry reliability
- [ ] Add Django-admin visibility for contact enquiries, failed email attempts and order/payment status.
- [ ] Add retry handling for failed transactional emails without creating duplicate emails or orders.
- [ ] Add a documented manual fallback process for enquiries or orders received while an external provider is unavailable.

## Working Rules

1. Tag or record the current known-good commit before risky work.
2. Use one feature branch per change.
3. Generate changes against the exact current commit.
4. Apply small, reviewable patches.
5. Never replace existing workflows wholesale.
6. Run available local checks and GitHub CI.
7. Merge through a pull request.
8. Deploy only after CI passes.
9. Update this file in the same pull request whenever a task changes status.
